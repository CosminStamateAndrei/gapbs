\section{Optimisations}
\label{sec:opt}

We chose every optimisation because of something we saw in the analysis or the model, and
every variant passes the BFS verifier. Figure~\ref{fig:opt} shows the speedups on
\texttt{kron20} and Table~\ref{tab:opt} the medians and IQRs. As explained in
Section~\ref{sec:method}, a difference only counts as significant if it is bigger than the
IQR of both configurations.

\subsection{O1: Compiler options and vectorisation}
\emph{Why.} This is the easiest thing to try and it was in our work plan. \emph{Result.}
\texttt{-O0} is about 2.5 times slower than \texttt{-O3} on both machines, \texttt{-O1} already
gets most of the speed back, and \texttt{-O2} and \texttt{-O3} are the same within the IQR.
\texttt{-march=native} is not faster (\SI{9.16}{ms} against \SI{8.01}{ms} on the laptop and
\SI{3.43}{ms} against \SI{2.75}{ms} on Hábrók, both within the IQR). The GCC report
(\texttt{-fopt-info-vec-all}) explains why: none of the important loops is vectorised. The
inner loop of \texttt{BUStep} is not vectorised because of \emph{control flow in loop} (the
\texttt{break}), its outer loop because of \emph{multiple nested loops}, and \texttt{TDStep}
because the atomic compare-and-swap \emph{clobbers memory}. To vectorise BFS one would need a
different formulation of the algorithm. For the same reason we did not try loop
transformations like unrolling or unroll-and-jam: the loops of BFS have trip counts that
depend on the data and early exits, and \texttt{-O3} already unrolls where it can. The model
also shows that the bottleneck is the memory, so the number of instructions does not matter
much once \texttt{-O1} has removed the obvious overhead.

\subsection{O2: OpenMP schedule, binding and number of threads}
\emph{Why.} Half of the samples are in the OpenMP runtime (Table~\ref{tab:hotspots}), and on
Hábrók the model does not explain a factor of 2.5 to 6.5 (Section~\ref{sec:model}).
\emph{What we changed.} \texttt{schedule(runtime)} for both loops, tested with chunk sizes
that are a multiple of 64 (Section~\ref{sec:method}), thread binding, and the number of
threads. \emph{Result.} No schedule is better than the original combination (static for
top-down, \texttt{dynamic,1024} for bottom-up). Using the same schedule for both loops is
slower on the laptop, and the best one on Hábrók (\texttt{static,64}, \SI{2.59}{ms}) is
within the IQR. Binding alone also makes no significant difference. The number of threads
does: on Hábrók, 48 threads bound to neighbouring cores (\SI{1.38}{ms}) are \textbf{2.1 times
faster} than the default of 128 unbound threads. They all run on one socket, so there is no
coherence traffic between the sockets and the barriers are smaller. On the laptop the best is
8 of the 10 vCPUs, but the difference is not significant.

\subsection{O3: Huge pages}
\emph{Why.} The latency curve (Figure~\ref{fig:latency}) goes up when the TLB is not big enough
anymore, and \texttt{BUStep} and \texttt{TDStep} access a CSR of \SI{136}{MB} at random.
\emph{What we changed.} \texttt{madvise(MADV\_HUGEPAGE)} on the CSR arrays and the
\texttt{pvector}s before they are first used. With \texttt{/proc/self/smaps\_rollup} we checked
that \SI{127}{MB} of the program then uses \SI{2}{MB} pages, and 0 without the patch.
\emph{Result.} On \texttt{kron20} all four laptop configurations are within each other's IQR.
On \texttt{kron22} the patch makes the median on the laptop \SI{29}{\percent} lower, but the IQRs
are above \SI{40}{ms}, so this is not significant. Hábrók already uses transparent huge pages
(\texttt{always}), so the original code already gets huge pages and the patch changes nothing:
about \num{4200} against \num{4900} dTLB misses per search, which is very little compared to
about 2 million random accesses. On the laptop, where TLB misses make the memory latency
higher (Figure~\ref{fig:latency}), the effect we hoped for is hidden by the noise of WSL2.

\subsection{O4: Software prefetching in top-down}
\emph{Why.} The random accesses to \texttt{parent[v]} in \texttt{TDStep} are limited by
latency, and prefetching a few neighbours ahead should give more open misses at the same
time. \emph{Result.} No prefetch distance is significant on either machine. The best is
distance 16 on Hábrók, \SI{11}{\percent} faster but within the IQR. The analysis already
predicted this: top-down is only \SI{3}{\percent} of the samples and \SI{11}{\percent} of the
modelled data, so even perfect prefetching could only save a few percent (Amdahl's law). In
the bottom-up step, where most time is spent, the loads for different vertices are already
independent, so the out-of-order core can overlap them.

\subsection{O5: Relabelling the vertices by degree}
\emph{Why.} The model shows that most of the data is one neighbour line per checked vertex in
bottom-up, plus the random accesses to \texttt{parent}. If we number the vertices by
decreasing degree (\texttt{-DRELABEL}, using \texttt{RelabelByDegree} from \gapbs), the vertices
with a high degree get small IDs that are next to each other, which gives better locality.
Because the neighbour lists are sorted, these vertices, which are most likely to be in the
frontier, are also at the start of every neighbour list. \emph{Result.} This is the best
optimisation: \textbf{2.4 times faster} on the laptop (\texttt{kron20}) and \textbf{1.8 times}
on Hábrók for \texttt{kron22}. On the laptop the median for \texttt{kron22} is even 2.8 times
lower, but there the IQR of the original code is too large to call it significant. Our edge
counter shows why relabelling works: a search examines \SI{35}{\percent} fewer edges on
\texttt{kron20} and \SI{48}{\percent} fewer on \texttt{kron22}, because bottom-up finds a parent
in the frontier earlier. So it reduces both $Q$ and the work. On \texttt{kron24} the gain (1.13
times) is not significant. \emph{Note.} The relabelling itself takes \SI{0.46}{s} for
\texttt{kron20}. This is not included in the search time and is paid back after about 90
searches on the laptop. After relabelling the vertices have other IDs, so the pseudo-random
sources are not the same as in the original runs.

\subsection{O6: First touch for NUMA}
\emph{Why.} \gapbs{} loads the graph with one \texttt{read()}, so one thread touches every page
first, and on Hábrók the whole edge array (\SI{125}{MB}) ends up on one socket. The threads on
the other socket then read everything from remote memory, and only the memory controllers of
one socket are used. \texttt{numactl} is not available on Hábrók, so we changed the code:
\texttt{-DPAR\_FIRST\_TOUCH} first writes zeros to the array in parallel and then reads the
file into it. \emph{Result.} The placement matters as soon as the threads are on both
sockets. With \texttt{OMP\_PROC\_BIND=spread} the original code becomes slower, \SI{4.00}{ms}
[IQR 1.17] on \texttt{kron20}, because half of the threads read everything remotely. With the
parallel first touch it takes \SI{1.94}{ms} [IQR 1.18], which is \textbf{2.1 times faster}, and
also 1.5 times faster than the default configuration. On \texttt{kron22} first touch is
\SI{11}{\percent} faster with spread binding (from 12.33 to \SI{10.96}{ms}, significant).
Without binding the gains are smaller and within the IQR, because the operating system places
the threads differently every time. On \texttt{kron24} the difference is not significant, and
we did not find out yet why the effect is gone for the largest graph.

\subsection{O7: The switching parameters $\alpha$ and $\beta$}
\emph{Why.} $\alpha$ and $\beta$ decide how much of the work is done in each of the two very
different steps. \emph{Result.} We tried 3 values for each ($3 \times 3$), and the default values
are already close to the best. With $\alpha = 5$ the search stays in top-down for too long and
is 4.4 times slower on the laptop. The best settings ($\alpha = 15$, $\beta = 36$ on the laptop
and $\alpha = 15$, $\beta = 9$ on Hábrók) are within the IQR of the default.
